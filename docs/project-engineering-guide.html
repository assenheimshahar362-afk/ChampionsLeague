01 · Mental model

The application is a time-gated prediction ledger

The UI is important, but the core system is a set of temporal and visibility invariants enforced close to the data.

Before kickoff

An authenticated, onboarded player may create or amend one prediction per fixture. Other players cannot read it.

At kickoff

Writes lock. Missing eligible picks are filled deterministically. Group predictions become visible.

After the result

The withheld regulation-time result is released and each prediction receives one idempotent score row.

Primary invariant: client clocks and UI disabled states are advisory. PostgreSQL policies, constraints and definer functions are the authority.

04 · Request lifecycle

How a localized page request executes

1. proxy.tsResolves locale, refreshes Supabase auth cookies and redirects protected anonymous requests.
2. Route segmentapp/[locale] validates the locale and supplies fonts, navigation, providers and live refresh.
3. Server pageFetches user-scoped data through query modules. Dynamic clock-dependent paths call connection().
4. Client islandReceives serializable props and owns only interaction state, dialogs, countdowns and optimistic feedback.
5. MutationA Server Action validates again, writes through RLS/RPC, then revalidates or refreshes affected views.

Localization

i18n/routing.ts defines en and he. Use the navigation exports from i18n/navigation.ts, not raw Next navigation, when the locale must be preserved.

Time

The server passes a request timestamp for lock decisions. Kickoffs are stored as timestamptz; the browser formats them in the viewer’s local timezone.

05 · Prediction lifecycle

One fixture, one user, one durable call

Open fixturefixtures.status = scheduled and kickoff_at > now().
Save actionlib/predictions/actions.ts validates scores and identity.
Database policyRLS independently verifies ownership and the kickoff boundary.
Kickoff fallbackensure_automatic_predictions() inserts deterministic missing picks.
Settlementprediction_scores becomes the authoritative awarded-points record.

Uniqueness

(user_id, fixture_id) is unique. A changed prediction is an update, never a second row. There is no client delete policy.

Joker rule

fixture_round is intentionally denormalized so a partial unique index can enforce one joker per user per round.

Blind play

A player sees their own pick immediately. Other players’ picks become readable only after the fixture starts.

Automatic pick

The fallback hashes user + fixture IDs. It does not use the known result, execution time or mutable random state.

06 · Live data and settlement

Polling and scoring are separate workflows

Live polling

lib/ingest/live.ts selects fixtures in the live window, claims a database-backed rate-limit slot, fetches provider matches in one call and updates public status plus withheld results.

Entry points: /api/cron/live and the viewer-driven /api/matches/live.

Settlement

lib/settle/run.ts first ensures missing predictions, then releases due results and upserts score rows. Repeated runs are expected and safe.

Entry point: /api/cron/settle; admin can also trigger settlement.

Scoring uses regulation time. Provider aggregate goals may include extra time. Ingestion stores the provider’s full-time pair used by the game and treats extra time as display-only.
07 · AI prediction pipeline

Research once, cache once, meter every call

ScopeNearest match week or explicit fixture, bounded by the configured horizon.
Reserve budgetAn advisory-lock RPC atomically reserves a conservative amount.
ResearchResponses API performs web search and returns validated structured bilingual output.
PersistPrediction, factors, sources, snapshot, model and timestamps are cached per fixture.
AccountToken categories, web calls and estimated cost complete the usage reservation.

The AI participant is virtual: it has no Auth account and no group membership. Its cached score predictions are projected into leaderboards and become authoritative only when normal fixture settlement is available.

Scheduler expectations
Vercel schedules daily ingestion only. A minute-capable external scheduler or suitable Vercel plan must call live polling and settlement with Authorization: Bearer $CRON_SECRET.
Observability currently available
Cron routes return structured reports; admin exposes participant completeness, settlement and AI cost state; provider quota metadata flows through the client. There is no dedicated tracing vendor configured.
Historical replay mode
REBASE_ENABLED=true remaps historical kickoff times around a pivot. The untouched time remains in original_kickoff_at. Live provider polling disables itself during replay to avoid leaking known results.
13 · Non-obvious rules

Read these before the first refactor

Bootstrap is destructive

0001_init.sql drops public. It is complete for a fresh project, not an upgrade script for populated production.

Results are intentionally duplicated

fixture_results withholds provider truth; released values are copied to fixtures only when the game timeline permits.

Status alone is insufficient

Prediction locks and visibility use kickoff time as a backstop because provider status can lag or a replay can shift the active timeline.

Cache components are enabled

Clock- or request-dependent data must opt into request execution correctly. Follow the local Next.js 16 docs before changing cache behavior.

Database types must track SQL

lib/supabase/database.types.ts is the compile-time contract. Regenerate it after deploying schema changes.

Free provider data is limited

Detailed lineups, events and scorer data may require Football-Data.org Deep Data. All detail fields therefore remain optional.

Never “fix” a permission problem by exposing the service-role key. Add the narrowest policy, grant or security-definer RPC that preserves the intended boundary.
14 · First-day plan

A practical onboarding sequence

  • Read README.md, docs/setup.md and the database diagram.
  • Populate .env.local and run npm run db:preflight.
  • Run npm run check to establish a clean baseline.
  • Trace one home-page request from proxy.ts through fixture queries to MatchList.
  • Trace one saved prediction through the Server Action and its RLS policy.
  • Read lib/ingest/live.ts and lib/settle/run.ts together.
  • Use a dry ingestion run before allowing any provider-backed write.
  • Make a small change with a focused test, then run the complete build.
